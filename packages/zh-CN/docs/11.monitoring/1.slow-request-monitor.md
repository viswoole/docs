# 慢请求监控

慢请求监控用于在请求耗时超过阈值时，把该请求的完整画像（元信息、参数、响应、数据库与缓存操作明细、异常）整理成一份已脱敏的 JSON 快照并持久化。整个采集链路对业务代码零侵入，是排查「这条请求为什么慢」的第一手工具。

## 核心组件

| 组件 | 全限定名 | 职责 |
| --- | --- | --- |
| MonitorService | `Viswoole\Monitor\MonitorService` | 服务提供者，注册配置与写入器绑定，启动时预热单例 |
| MonitorOptions | `Viswoole\Monitor\MonitorOptions` | 承载全部静态配置并在构造时校验，提供路径采集判定 |
| MonitorRuntime | `Viswoole\Monitor\MonitorRuntime` | 共享运行态：运行时全局阈值与精确接口覆盖规则的跨进程管理 |
| CapturePolicy | `Viswoole\Monitor\Runtime\CapturePolicy` | 请求开始时固定的采集策略（配置版本、命中规则与有效阈值） |
| SlowRequestMonitor | `Viswoole\Monitor\SlowRequestMonitor` | 管理单次请求的采集生命周期（开始/结束/持久化） |
| TraceContext | `Viswoole\Monitor\TraceContext` | 协程上下文采集入口，供数据库/缓存等采集点计时 |
| TraceWriterInterface | `Viswoole\Monitor\Contract\TraceWriterInterface` | 快照持久化契约，可替换为外部系统 |
| JsonTraceWriter | `Viswoole\Monitor\Writer\JsonTraceWriter` | 内置文件日志写入器 |
| MonitoredDriver | `Viswoole\Cache\MonitoredDriver` | 缓存商店监控装饰器，自动采集缓存操作 |

`MonitorService` 已在框架核心服务列表中注册，无需手动添加——只需提供配置文件即可。

## 启用监控

框架自带 `config/monitor.php` 配置模板（位于框架包内），将其复制到应用的 `config/` 目录后修改两项即可：

```php
// config/monitor.php
return [
  // 总开关，修改后需重启服务生效
  'enabled' => true,
  // 启用时必须显式指定写入器，或在服务提供者中绑定 TraceWriterInterface
  'writer'  => \Viswoole\Monitor\Writer\JsonTraceWriter::class,
  // 慢请求阈值（毫秒），达到该值才写入记录；0 表示记录全部请求（开发调试用）
  'threshold_ms' => 1000,
  // ...其余配置见下文
];
```

默认写入器把快照写入 `runtime/slow-requests` 目录，复用框架文件日志的 JSON 编码、按日分目录、轮转与过期清理机制：

```bash
ls runtime/slow-requests/
# 2026-11-15/
#   slow_request_xxxx.json
```

::: warning:必须配置 writer
`enabled => true` 而未配置 `writer` 且未在服务提供者中绑定 `TraceWriterInterface` 时，服务启动即抛出异常——框架故意让配置错误尽早暴露，而不是等到第一个慢请求才失败。
:::

## 配置项总览

| 配置项 | 默认值 | 说明 |
| --- | --- | --- |
| `enabled` | `false` | 总开关，修改后需重启服务生效 |
| `writer` | `null` | `TraceWriterInterface` 实现类名；内置 `JsonTraceWriter::class` |
| `threshold_ms` | `1000` | 慢请求阈值（毫秒），`0` 表示记录全部请求；可经 `MonitorRuntime` 运行时调整 |
| `override_capacity` | `256` | 精确接口覆盖规则的共享存储容量，启动时分配，运行时仅在容量内增删改 |
| `capture_request` | `true` | 是否采集请求元信息与参数；关闭时快照仅保留方法/路径 |
| `capture_response` | `true` | 是否采集响应；关闭时仍保留状态码、字节数和完成信息 |
| `capture_database` | `true` | 是否采集数据库操作 |
| `capture_cache` | `true` | 是否采集缓存操作 |
| `exclude_paths` | 见配置模板 | 不采集的路径列表，支持 fnmatch 通配符 |
| `request_id.*` | 见下文 | 请求关联 ID 的生成与响应头 |
| `max_body_bytes` | `8192` | 单请求正文采集上限（字节），超限默认不输出正文，可配 `body_truncator` 保留业务摘要 |
| `body_truncator` | `null` | 正文超限时的自定义摘要处理器（callable），契约见 [隐私与采集预算](2.privacy-and-limits.md#自定义正文裁剪) |
| `max_operations` | `200` | 单请求操作记录条数上限，超限计入 `dropped_operations` |
| `max_snapshot_bytes` | `262144` | 快照总 JSON 字节预算，最低 16 KiB |
| `record_bindings` | `false` | 是否记录 SQL 绑定值 |
| `record_sql` | `false` | 是否记录 SQL 原文（默认仅 SHA-256 摘要） |
| `privacy.defaults` | 见配置模板 | 按「方向 × 分组」的全局采集开关与脱敏字段 |
| `privacy.rules` | `[]` | 按路径（可选方法）追加的采集与脱敏规则，见 [隐私与采集预算](2.privacy-and-limits.md#隐私配置privacy) |

隐私类配置（脱敏、SQL、绑定值）的详细行为见 [隐私与采集预算](2.privacy-and-limits.md)。

## 排除无需观测的路径

健康检查、静态资源等高 QPS 且无观测价值的路径应显式排除，避免为它们支付采集成本：

```php
// config/monitor.php
'exclude_paths' => ['/health*', '/favicon.ico', '/static/*', '/assets/*'],
```

匹配语义与路由一致：

- 支持单次逐段 URL 解码与尾斜线处理；
- 大小写是否敏感跟随 `router.case_sensitive` 配置；
- 完整路径与去伪静态后缀的候选路径**任一命中即排除**，采集开始前采用更严格的保护并集。

## 请求关联 ID（Request ID）

每条快照都携带一个 `request_id`，用于把慢请求记录、应用日志与客户端反馈串联起来：

```php
// config/monitor.php
'request_id' => [
  // 默认 bin2hex(random_bytes(16))，128 位随机，碰撞概率极低但非零；
  // 严格唯一请传入自己的发号器（支持任何无参 PHP callable，返回 string|int）
  'generator' => null,
  // 非空标头名称启用后，每个响应都会携带该头（含未达到阈值的快请求）
  'response_header' => 'X-Request-Id',
],
```

- 自定义生成器返回 `string` 或 `int`（兼容雪花发号器），长度限制为 1~256 字节可见 ASCII；
- 生成失败时**跳过本次监控**，不会降级成随机 ID 破坏自定义发号器的唯一性承诺；
- 业务代码中可随时通过 `TraceContext::requestId()` 读取当前请求的 ID（未启用监控时为 `null`）：

```php
use Viswoole\Monitor\TraceContext;

TraceContext::requestId(); // "9f86d081884c7d65...", 与响应头和快照一致
```

## 运行时阈值与接口覆盖规则

`MonitorOptions` 中的静态配置在服务启动时固化；而 `MonitorRuntime` 维护一份**跨 Worker 共享的运行态**（基于 Swoole Table），支持在不重启服务的前提下调整全局阈值、增删精确接口覆盖规则。框架不内置管理命令——规则授权、排期与持久化由项目自行负责（共享运行态存活于进程内存，服务重启后规则清空，需由项目重新发布或恢复）。

### 全局阈值

```php
use Viswoole\Monitor\MonitorRuntime;

$runtime = app(MonitorRuntime::class);          // 或通过容器注入类型

$runtime->getThresholdMs();                     // 读取当前全局阈值
$runtime->setThresholdMs(500.0);                // 原子更新，相同值不推进版本
```

### 精确接口覆盖

覆盖规则把某**一个已注册接口**的采集阈值单独调低（或调高），适合「个别慢接口需要更细粒度观测」的场景：

```php
use Viswoole\Core\Facade\Router;
use Viswoole\Monitor\MonitorRuntime;

$runtime = app(MonitorRuntime::class);

// 从路由目录获取精确接口身份（每个方法及别名单独列项）
$target = null;
foreach (Router::getInterfaces() as $interface) {
    if ($interface->method === 'GET' && $interface->template === '/api/report/summary') {
        $target = $interface;
        break;
    }
}

// 为该接口发布 200ms 的独立阈值；id 用于后续增删与排障关联
$runtime->setOverride('report-summary', $target, 200.0);

$runtime->getOverrides();    // 列出全部规则（不可变值）
$runtime->removeOverride('report-summary'); // 删除，规则不存在时版本不变
$runtime->getState();        // 一次一致性读取全局值、实例、版本与规则
```

语义与约束：

- **精确身份，不支持通配**：规则目标是 `RouteIdentity`（方法 + 注册模板 + 域名约束），不能传实际 URL，也不支持路径前缀或 fnmatch 匹配；目标必须在路由目录中唯一存在（`OPTIONS` 预检不提供覆盖身份）；
- **发布时机**：路由初始化完成（`RouterInitialized` 事件之后）才能发布规则，`Router::getInterfaces()` 过早调用会抛出 `LogicException`；
- **规则 ID**：1~64 个字母、数字或 `_.:-`，请勿在 ID 中存放个人信息；
- **容量与版本**：新增规则受 `override_capacity` 限制，每次变更推进全局配置版本；
- **有效阈值**：请求命中多条规则时取 `min(全局阈值, 命中规则阈值)`。

### 请求策略固定

每个请求开始采集时，框架会**固定当时的配置版本与命中规则**（`CapturePolicy`），之后的运行时变更不影响进行中的请求，保证一次请求内的判定一致。达到阈值的快照会携带 `capture` 字段记录完整采集依据（见下文快照记录结构），写入器可据此区分「正常慢请求」与「接口覆盖规则命中」两种来源。

## 快照记录结构

达到阈值后写入的 JSON 记录（`schema_version` 标识结构版本，升级框架时可用于兼容判断）：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `request_id` | string | 请求关联 ID |
| `timestamp` | string | 快照生成时间 |
| `duration_ms` | float | 请求总耗时（毫秒） |
| `response_time_ms` | float \| null | 首次响应耗时（毫秒），流式响应时区分于总耗时 |
| `request` | object | 方法、路径、host、IP、请求头、query/post/body/files、路由信息 |
| `response` | object | 状态码、Content-Type、响应头、正文、重定向目标、sendfile 信息 |
| `operations` | list | 操作明细（database / cache / other 三类），每条含耗时与结果摘要 |
| `operation_summary` | object | 按类型聚合的统计（次数、总耗时、失败数） |
| `dropped_operations` | int | 超出 `max_operations` 被丢弃的操作条数 |
| `exception` | string \| null | 请求处理过程中抛出的异常类名 |
| `capture` | object \| null | 采集来源（版本 2 新增）：`runtime_id`、`config_version`、`route_identity`（精确接口身份）、`global_threshold_ms`、`effective_threshold_ms`、`matched_global`、`matched_overrides`（命中的覆盖规则及其版本） |
| `schema_version` | int | 快照结构版本号（当前为 2） |
| `snapshot_truncated` | bool | 是否因总字节预算被截断 |

操作明细字段按类型区分：

- **database**：`channel`（连接通道）、`sql`（默认 SHA-256 摘要）、`bindings`（默认隐藏）、`binding_count` 等；
- **cache**：`store`（商店名）、`operation`（get/set/...）、`key`（缓存键）、`tags`（标签）；
- **other**：其他被计时的操作，仅保留类型与耗时汇总。

请求/响应的 `body` 字段按采集状态分四种形态：

- 分组关闭（`privacy` 中对应方向 `body.capture => false`）：`content` 为 `[CAPTURE_DISABLED]`，`bytes` 等元信息仍保留；
- 未超限：`content` 为解析后的结构化数据（JSON 或表单）或原始文本，`truncated` 为 `false`；
- 超限且未配置处理器：`content` 为 `[BODY_LIMIT]` 占位，`bytes` 保留真实字节数；
- 超限且配置了 `body_truncator`：`content` 为处理器返回、已完成脱敏的摘要数组，与 `truncated: true` 并存；处理器失败或摘要超限时回退为占位（见 [自定义正文裁剪](2.privacy-and-limits.md#自定义正文裁剪)）。

## 运行边界与故障行为

监控是旁路设施，理解它的边界有助于放心在生产开启：

- **采集失败不影响业务**：监控内部任何异常只触发 `E_USER_WARNING` 告警（仅记录异常类型，避免消息泄露 DSN、账号等敏感信息），请求照常处理；
- **先清理再持久化**：写入快照前已清理请求上下文，因此写入器内部的数据库、缓存调用不会被递归采集；
- **未达阈值零写入**：未达到 `threshold_ms` 的请求只维护内存中的采集状态，不产生 IO；
- **静态配置启动期校验**：阈值非法、预算越界、列表含空字符串、未知配置键、已废弃的旧敏感字段配置（`sensitive_keys` / `sensitive_keys_by_path`）等错误在服务启动时即抛出，不会拖到请求中途；
- **修改静态配置需重启**：`MonitorOptions` 层面的配置（采集开关、预算、隐私规则等）在服务启动时读取并固化，热更新无效；全局阈值与接口覆盖规则经 `MonitorRuntime` 运行时调整（见上文），重启后运行态规则需由项目重新发布；
